H1: Save/load destroys sealed dead-end maps, breaking the region seal
-----------------------------------------------------------------------
[VERIFIED]

Reproduction (gameplay):
  1. Clear a region's village so sealRegion() runs and stamps dead-end neighbours
     on every unused border in that region.
  2. Save to a named slot.
  3. Load that slot.
  4. Walk into any dead-end map you had not personally entered before saving.

Reproduction (console, faster):
  1. const id = createSealedNeighbor(currentMapId, 'left');
  2. Note worldMaps[id].sealed, its open borders (mapEdgeOpen), and that it holds a
     LARGE_CHEST (the Hero's Cache).
  3. applyLoadData(JSON.parse(JSON.stringify(buildSaveData())));
  4. Re-inspect worldMaps[id].

Actual (measured on the round-trip above):
                       before save        after load
    open sides         right only         ALL FOUR
    sealed flag        true               absent
    Hero's Cache       1 LARGE_CHEST      0 (downgraded to a plain CHEST)
    terrain            —                  completely regenerated, unrelated map

Expected: a dead-end returns from a load with exactly one open border (facing its
source map), its `sealed` flag intact, its Hero's Cache intact, and identical terrain.

Location / causes — three separate defects compound here:
  1. save.js:46   `mapTiles: m.visited ? encodeMap(m.map) : null`. sealRegion creates
                  dead-ends with `visited: false` (world.js:585), so their tiles are
                  never written to the save at all.
  2. save.js:305  the rebuild path calls
                  `buildRegionMap(lite.id, lite.depth, undefined, region)` — openSides
                  is `undefined`, and mapgen-biomes.js:637 defaults that to
                  `{left:true, right:true, up:true, down:true}`.
  3. save.js:37-89 the `worldMapsLite` projection has no `sealed` field, so the flag
                  is silently dropped.

Impact:
  - The core "clearing a village seals the region" mechanic unravels after any
    save/load. A four-exit dead-end lets the player walk back out into a region they
    already sealed and left, generating fresh maps behind the seal.
  - Border symmetry breaks. The neighbouring map's tiles ARE stored, so the
    regenerated dead-end opens toward a neighbour with no opening back — exactly the
    one-way doorway reconcileOpenSides (world.js:60-69) exists to prevent. That
    reconcile runs only at creation time, never on load.
  - The Hero's Cache — the reward for taking the dead-end detour — is silently
    downgraded to an ordinary chest.
  - Three other systems read the dropped `sealed` flag and change behaviour without it:
      player.js:905     sealed maps are excluded from regionMapsVisited. After a load
                        they count, inflating progress toward the 21-map village trigger.
      guild.js:143,333  Guild Quarry and bounty elites filter on `!mm.sealed`. After a
                        load, quest targets can spawn on dead-end maps.
      abilities.js:296  ability secrets are deliberately not stamped on sealed maps.
                        After a load they become eligible.
  - Scale: only maps the player personally entered are stored by tile. Dead-ends are
    created without being entered, so this affects most of them across all 13 regions.

Recommended fix (does NOT require the seed work — do this now):
  - Add `sealed` and the four resolved open-side booleans to the worldMapsLite
    projection in buildSaveData().
  - Pass those open sides into the rebuild call at save.js:305 instead of `undefined`.
  - Re-run reconcileOpenSides() after rebuilding any map from a builder, so a
    regenerated map can never open toward a neighbour that does not open back.
  - Either store `mapTiles` for sealed maps regardless of `visited`, or move the
    Hero's Cache upgrade (world.js:565-579) into the rebuild path so it is reapplied.

H2: A completed save exceeds localStorage, and the autosave fails silently
-----------------------------------------------------------------------
[VERIFIED]

Reproduction (measurement):
  1. ensureFog(currentMap()); revealAround(currentMap(), 75, 75, 60);
  2. JSON.stringify(encodeMap(currentMap().map)).length      -> 30,002 chars
  3. JSON.stringify(Array.from(currentMap().fog)).length     -> 45,001 chars

Actual: fog serializes via `Array.from()` into a JSON array of 22,500 numbers —
45,001 characters per map, or 1.5x the size of the entire base64 tile map, to carry
one bit of information per tile.

  per visited map:  30,002 (tiles) + 45,001 (fog) = 75,003 chars
  x 232 maps (the figure the save UI itself advertises, save.js:491 and :522):
                    ~16.6 MB per slot, of which ~10 MB is fog
  and six named slots plus the rolling autosave share one origin quota.

Measured ceiling in the Chromium used for testing: 48.5 MB — so one completed save
fits there, but two do not. The README documents touch/phone support as a first-class
target; iOS Safari's ~5 MB per-origin cap is a hard wall reached at roughly map 68
of 232.

CAVEAT on that 48.5 MB figure: it was measured over http://localhost:8765 (the
.claude/serve.ps1 test server). The game is actually played by double-clicking
index.html, and file:// pages get a different, generally more restrictive storage
bucket. The per-map costs above are origin-independent and stand as measured; the
ceiling should be re-measured under file:// before anyone concludes there is headroom.

Expected: a completed save comfortably inside a 5 MB budget, and any save failure
surfaced to the player.

Location:
  save.js:45   `fog: m.fog ? Array.from(m.fog) : null`
  save.js:450  `catch (e) { /* storage full — skip the autosave silently */ }`

Impact — the failure mode is the serious half. Verified by stubbing
Storage.prototype.setItem to throw QuotaExceededError:
  - doSave   reports it: "Save failed (storage full?)"     (save.js:598)  — correct.
  - autoSave shows NOTHING, and leaves `lastCheckpoint` pointing at the previous
    payload. Since respawn() restores from lastCheckpoint (player.js:472), the player
    keeps clearing villages and tower floors while their death-restore point silently
    stops advancing. The only cue is the ABSENCE of the "Auto-saved" toast they
    normally see on every checkpoint.

Recommended fixes — two independent changes:
  1. IMMEDIATE, one line: make autoSave's catch report the failure (a toast at minimum;
     a persistent HUD warning is better, because a checkpoint that has quietly stopped
     advancing is the kind of bug players only discover by losing hours).
  2. Bit-pack fog and base64 it: 22,500 bits -> 2,813 bytes -> ~3,752 chars, a ~12x
     reduction that takes the projected save from ~16.6 MB to ~7.2 MB on its own. Fog
     is large contiguous runs, so RLE would do better still.
  See the PLANNED WORK section for how seeding takes this the rest of the way down.

H3: The Save/Load modal neither freezes the world nor captures input
-----------------------------------------------------------------------
[VERIFIED]

Reproduction:
  1. Start a game.
  2. Press V -> select the MENU ring -> "Game Menu" (gear) -> "Save Game".
  3. Click an empty slot to reveal the name field.
  4. Try to type a save name containing a space, e.g. "My Save".

Actual, with the name field focused:
    Space              preventDefault() fires — THE SPACE IS NEVER TYPED
    v                  opens the radial menu ON TOP of the save modal
    ArrowUp/ArrowDown  swallowed; also steps the hero
    z                  swings the sword
    p                  drinks a health potion
    Tab                toggles the minimap
  and the world keeps running underneath: with the modal open, a single update(16)
  moved the hero. Since stepPlayerMovement ends in tryTransition() (player.js:1888),
  the player can walk off the map edge while the save dialog is up.

Expected: the save/load modal behaves like every other overlay — world frozen,
gameplay keys inert, and the name field accepting ordinary text.

Location:
  main.js:101-111  the update() freeze chain lists radialMenuOpen, ledgerOpen,
                   statsPageOpen, worldMapOpen, sysMenuOpen, victoryOpen,
                   dialogueOpen, cutsceneBlocking — but has no term for `modalMode`.
  main.js:241-378  the keydown handler has a branch for every one of those overlays
                   and none for this one.
  save.js:681-684  the modal-name-input keydown listener does not stopPropagation.
                   Contrast main.js:78-82, where the hero-name input does exactly that
                   and is consequently correct.

Impact: every player hits this the first time they name a save. Save names cannot
contain spaces; typing a name that happens to include the game's hotkey letters fires
those actions; and the hero can be killed, moved, or walked onto another map while the
dialog is open.

Recommended fix:
  - Add `modalMode` (or an explicit saveModalOpen flag) to both the update() freeze
    chain and the keydown overlay chain.
  - Add e.stopPropagation() to the modal-name-input listener, matching name-input.

M1: Shop and portal modals do not freeze the world
-----------------------------------------------------------------------
[VERIFIED]

Reproduction:
  1. Enter a cleared (activated) village.
  2. Hold an arrow key and press Space next to a shopkeeper to open their shop
     (villagers.js:1264-1265 — shops open by talking, not by stepping on a door).
  3. Keep holding the arrow key.

Actual: the hero keeps walking underneath the open shop modal. Verified directly —
one update(16) with shopOpen true moved the hero.

Expected: the world is frozen while a shop is open, as it is for the ledger, stats
page, world map and game menu.

Location: same root cause as H3. shopOpen and portalOpen gate keyboard input
(main.js:262, :271) and canvas touches (main.js:507-517), but neither appears in the
update() freeze chain at main.js:101-111.

Impact: mostly masked today, because shops only open in cleared villages where nothing
is alive to hurt the player. But the hero still walks, villagers still step, and
tryTransition() can still fire — so it is possible to leave the map with a shop modal
still on screen. It is also why closeShopModals has to force-clear the whole `keys`
object at shop-core.js:60; that workaround is treating the symptom.

Recommended fix: add shopOpen and portalOpen to the update() freeze chain, then remove
the defensive key-clearing at shop-core.js:60 once it is no longer load-bearing.

L3: Duplicate overlay click listeners in shop-core.js
-----------------------------------------------------------------------
[BY INSPECTION]

Location: shop-core.js:64-75 registers the same outside-click handler twice — once
inside a DOMContentLoaded callback, once immediately as a "fallback for when the script
loads after DOMContentLoaded already fired". Classic (non-deferred) scripts at the end
of <body> run BEFORE DOMContentLoaded, so both always register.

Impact: harmless in practice — closeShopModals is idempotent — but the fallback is dead
weight and the doubled handler is misleading to read.

Recommended fix: keep only the immediate registration and delete the DOMContentLoaded
wrapper.

L4: Map generation is non-deterministic; `seed` is accepted and ignored
-----------------------------------------------------------------------
[VERIFIED]

Reproduction:
    python tools/lint-conventions.py
    -> 0 errors, 68 warnings, all "Math.random() in generation code -- same seed
       must give same map"

Actual: buildForestMap(seed, ...), buildDesertMap(seed, ...) and
buildRegionMap(seed, ...) all accept a `seed` parameter and none of them use it.
Generation runs entirely on bare Math.random()/rnd().

Location: mapgen-biomes.js:117, :466, :636 (signatures); the 68 call sites the linter
lists; world.js:244 and :546 (where the unused seed is passed).

Impact: this is what makes H1 destructive rather than merely lossy — a regenerated map
is not a slightly different version of the original, it is an entirely unrelated one.
It also blocks the permanent fix to H2, makes bug reports about specific maps
irreproducible, and leaves tools/seed-preview.html unable to do the job it was built
for.

Note: this is NOT a new discovery. The project's own conventions document
(.claude/skills/the-rpg-game/SKILL.md) already records it as a known pre-existing gap,
and sets the bar for fixing it: "threading an actual seeded PRNG through every
generation file that currently ignores `seed` — not just changing one call site and
calling it done." The plan below is scoped to meet that bar. It is listed here because
H1 and H2 both trace back to it, not because it was unknown.

Recommended fix: see the dedicated section below. This is a project, not a patch.

=======================================================================
PLANNED WORK — TRANSITION TO SEED-BASED GENERATION
=======================================================================

STATUS: not started. Recommended AFTER H1, H2's autosave fix, H3 and M1 have landed —
none of those depend on this, and all of them are small.

WHAT THIS IS AND IS NOT
  It will NOT make maps look better. A seeded PRNG produces the same distribution as
  Math.random(); the generated terrain is aesthetically identical. What it buys is
  REPRODUCIBILITY, and reproducibility is what lets the save stop storing tiles.

  Projected save budget, per visited map:

                       now              seeded
    tiles              30,002 chars     ~64 bytes  (seed + generation inputs)
    player edits       —                ~200 bytes (tile diff)
    fog                45,001 chars     ~3,752     (bit-packed, from H2)
    ----------------------------------------------------------------
    x 232 maps         ~16.6 MB         ~0.9 MB

  Secondary wins: tools/seed-preview.html starts working as designed; bug reports can
  name a reproducible world ("region 4, cell (3,-2), world seed 12345"); shareable
  world seeds become available as a player-facing feature.

CURRENT STATE — the groundwork is better than expected
  - The `seed` parameter is already threaded through buildOverworldForRegion ->
    buildForestMap / buildDesertMap / buildRegionMap. No signature changes needed.
  - 157 of the randomness call sites funnel through ONE function, rnd() at
    map-helpers.js:26. Replacing its body converts two-thirds of the generator in a
    single edit:
        mapgen-biomes.js   95     mapgen-tower.js     8
        mapgen-foliage.js  19     mapgen-caves.js    17
        mapgen-terrain.js  15     mapgen-village.js   3
  - The remaining direct Math.random() calls must be converted by hand:
        mapgen-biomes.js   25     mapgen-village.js  19
        mapgen-foliage.js  14     mapgen-terrain.js   7
        connectivity.js     1  (inside the rescue-corridor carve loop, which runs
                                during generation and therefore must be seeded too)
    plus, if enemy and name placement should also be reproducible:
        enemies.js          5     world.js            3  (map name selection)
  - tools/seed-preview.html already calls
    buildOverworldForRegion(regionIdx, seed, depth, openSides, false) and expects the
    seed to matter, so the verification harness exists on day one.

THREE HAZARDS — each of these will silently defeat the migration if missed

  1. DO NOT SEED ON THE MAP ID.
     world.js:244 currently passes `id` as the seed, and `id` is worldMaps.length at
     creation time. It shifts depending on how many caves, grottos, dungeons and sky
     caves the player happened to open first, so two players walking identical routes
     get different ids for the same place. The stable identity of an overworld map is
     its grid cell. Seed on hash(worldSeed, gx, gy), and persist worldSeed in the save.

  2. A SEED ALONE DOES NOT MAKE A MAP REPRODUCIBLE.
     The generated map is a function of (seed, depth, openSides, placeDungeon, region),
     and three of those five are path-dependent world state rather than properties of
     the cell:
        depth        Math.min(regionMapsVisited[r] + 1, 20)  — visit order
        openSides    reconcileOpenSides(...)                 — which neighbours existed
        placeDungeon regionDungeonPlaced[r]                  — first map past depth 3
     All three must be persisted alongside the seed (they are a handful of bytes) or
     made derivable. Skipping this produces a deterministic generator that still
     returns a different map — the worst of both worlds, because the failure is quiet.

  3. A DIFF LAYER IS REQUIRED.
     A seed regenerates the PRISTINE map. The tile array is then mutated at runtime by,
     at least: cut foliage (projectiles.js:425), bombed rocks and snow drifts,
     placeVillageBossChest, the whirlpool-grotto chest (player.js:769-770), sealed
     shrines converted by tryUnsealShrine, installVillageShrineEntrance, and the
     ability-secret alcoves stamped by ensureAbilitySecret. Store a list of
     (tileIndex, tileValue) pairs. A few dozen edits per map is ~200 bytes against the
     30,000 being saved, so this is cheap — but it is not optional.

PHASED PLAN — each phase ends at a verification gate; do not proceed past a red gate

  Phase 0 — Spike (half a day). Do this before committing to the rest.
    Add a small PRNG (mulberry32 or xorshift32 — both are ~5 lines and more than good
    enough for terrain). Route rnd() through it. Thread a seed into buildForestMap only.
    GATE: generate the same cell twice in tools/seed-preview.html and diff the tile
    arrays. Identical -> the remaining conversions are mechanical, continue. Different
    -> hidden state is leaking into generation; find it now, before converting 66 more
    call sites on top of a broken foundation.

  Phase 1 — Convert the generator.
    Replace the ~66 direct Math.random() calls in the generation path with the seeded
    stream. Include connectivity.js:102. Decide explicitly whether enemy placement
    (enemies.js) and map names (world.js:231, :548) join the deterministic set — names
    are cosmetic but player-visible, so inconsistent names across a reload look like a
    bug even when the terrain matches.
    GATE: tools/lint-conventions.py reports 0 Math.random() warnings in generation
    files. Generate all 13 regions at several depths twice each in seed-preview and
    diff every tile array.

  Phase 2 — Persist the recipe.
    Add worldSeed to the save. Add per-map { seed, depth, openSides, placeDungeon } to
    the worldMapsLite projection. Keep writing mapTiles as well for now — this phase
    changes nothing about what is loaded, it only starts recording what would be needed.
    GATE: for every map in a real save, regenerate from the recorded recipe and diff
    against the stored mapTiles. All must match.

  Phase 3 — Add the diff layer.
    Capture post-generation tile mutations per map. Simplest correct implementation:
    on save, diff the live map against a fresh regeneration from its recipe and store
    the differing cells. That needs no new instrumentation at the ~12 mutation sites
    and cannot miss one.
    GATE: recipe + diff reproduces the live map byte-for-byte across a full save/load
    on a late-game save.

  Phase 4 — Drop mapTiles; pack fog.  *** REQUIRES EXPLICIT SIGN-OFF ***
    Stop writing mapTiles. Land the H2 fog bit-packing at the same time.
    This is the one phase that changes the persistence format, which the project's
    conventions (SKILL.md, "Save compatibility") require flagging before it happens
    rather than after: "Never change the persistence mechanism or the slot format
    without flagging it first and saying explicitly that existing saves will break."
    Per the compatibility plan below, existing saves are designed NOT to break — they
    keep their stored mapTiles and keep loading through decodeMap. But the format
    written from this phase onward is new, and a save written after Phase 4 will not
    load in a build from before it. Confirm that trade before starting, not during.
    GATE: measure a late-game save. Target under 1 MB. Then load a REAL named save
    written before the change (per SKILL.md's verification rule — an existing save,
    not just a new game), and play a full region start to finish on the new format,
    confirming no visual or progression differences.

  Phase 5 — Cleanup.
    Remove encodeMap/decodeMap if nothing else uses them. Update the save-format notes
    in save.js's header comment. Consider exposing the world seed in the UI.

BACKWARD COMPATIBILITY
  Old saves have no worldSeed, no recipes and no diffs, but they DO have mapTiles.
  Keep the decodeMap path as the fallback for any map carrying stored tiles, exactly as
  the existing migrations do (see homeLayoutVersion, save.js:282-284, and the
  hasBow/hasSword back-fills at save.js:224-240 for the established pattern). Old saves
  keep their exact worlds; only new maps generated after the upgrade use recipes.
  Do NOT attempt to back-fill seeds for existing maps — their terrain was produced by
  an unseeded generator and cannot be recovered from a seed by construction.

RISK
  Medium, and concentrated in Phase 1 (mechanical but wide) and Phase 3 (subtle). The
  Phase 0 gate is what makes the whole thing safe to abandon cheaply: if the spike
  cannot reproduce a single map twice, stop, and the only cost is a few hours plus a
  PRNG that is worth having regardless. Phases 0-2 are non-breaking — nothing about
  what the game loads changes until Phase 4.

RECOMMENDED ORDER OF WORK
=======================================================================

  1. H2, autosave catch only          one line; turns a silent failure into a visible one
  2. H3 + M1                          freeze chain + stopPropagation; small, contained,
                                      and H3 is hit by every player who names a save
  3. H1                               persist sealed + open sides; re-run
                                      reconcileOpenSides after rebuild. This is the one
                                      that quietly corrupts long playthroughs.
  4. H2, fog bit-packing              ~12x on the dominant cost

  L4  THE PHASE 0 GATE CAUGHT A REAL MISS — which is what it was for. After converting
      all 66 direct Math.random() calls in mapgen-*.js and connectivity.js, the same
      seed STILL produced different maps. Cause: map-helpers.js had 14 more calls of
      its own, in the drunkWalk corridor carvers that every builder leans on. It is not
      a mapgen-* file, so the sweep missed it. Converting those turned the gate green.
      Had this been taken on faith, the whole save-size change would have been built on
      a generator that only looked deterministic.

      map-helpers.js  mulberry32 PRNG, hashSeed (FNV-1a), and a module-level generation
                      stream that builders swap in for the duration of a build and
                      restore on the way out (nestable). rnd() reads the stream;
                      genRandom() is the direct-call form. Default is Math.random, so
                      runtime rnd() callers (enemies, player, render, tower, villagers)
                      stay non-deterministic — a reloaded save must not replay
                      identical loot rolls. Also tileHash().
      mapgen-*.js     66 conversions; connectivity.js 1; map-helpers.js 14.
      mapgen-biomes.js the three overworld builders seed on entry and restore on exit.
      world.js        worldSeed rolled per world; each map seeded on hashSeed(worldSeed,
                      gx, gy) — the GRID CELL, not the map id. id is worldMaps.length at
                      creation and shifts with how many caves/grottos the player opened
                      first, so it would seed the same place differently between runs.
                      Map names seed off the cell too, derived from the seed rather than
                      drawn from the stream so editing a name pool never shifts terrain.
      save.js         persists worldSeed, and per map: mapSeed, placeDungeon,
                      pristineHash (alongside openSides / sealed from the second pass).
                      placeDungeon matters — it is decided from mutable world state, so
                      a rebuild without it silently dropped the region's only dungeon.

      VERIFIED  same seed -> byte-identical map for forest, desert and all 13 regions;
                different seed and different depth both diverge; regions don't collide
                on a shared seed; dead-end topology reproduces exactly; unseeded callers
                and runtime rnd() remain random; the stream restores after every build.

  SAVE SIZE — the point of all of the above
      A seeded map that gameplay has not touched need not be stored at all. save.js
      hashes the live tiles against pristineHash and stores them only when they differ.

      DEVIATION FROM THE PLAN: Phase 3 called for a tile-diff computed by regenerating
      each map at save time. Measured, that is ~5.8 ms per map — ~1.5 s to save a full
      world, on every autosave. Rejected. Hashing answers the same clean/dirty question
      at ~0.05 ms per map, so the whole world is checked in a couple of milliseconds and
      only genuinely modified maps pay for their tiles. Modified maps still store full
      tiles rather than a sparse diff; that is the remaining refinement, worth roughly
      another 1.5 MB, and it is not needed to get under budget.

      VERIFIED  clean maps store no tiles, the dirty map stores them and keeps its
                edits, every map restores byte-identically, save build takes 1.7 ms.
      RESULT    11,543 chars per map, ~2.55 MB projected at 232 maps.
                Was 75,003 chars per map, ~16.6 MB. A 6.5x reduction.
